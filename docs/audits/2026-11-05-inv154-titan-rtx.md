# INV-004 TITAN RTX Windows repetition and results

The prospective registration is preserved below as historical registration text.
[Completed campaign findings](#completed-campaign--2026-11-05) supersede its
execution-pending status; they do not rewrite the registered protocol.

## Registered question and evidence boundary

**Planned experiment, registered 2026-11-05:** repeat the existing Windows
`space_step()` diagnostic on the identified local TITAN RTX host. Determine
whether the long-step tail reproduces in this host cohort and, if enough events
occur, classify calling-thread CPU occupancy using the existing registered
thresholds. Preserve worker and thread-state evidence where the host permits
capture. This registration contains no findings from the new campaign.

The [original Windows audit](2026-11-05-inv154-windows-thread-time.md) and
[Rayon worker audit](2026-11-05-inv154-rayon-workers.md) retain their own tested
sources, hosts, failures and artifacts. Earlier local observations do not count
as repetitions of this newly registered six-process campaign.

## Fixed workload and trial order

**Planned:** run six fresh Godot processes serially on the same host, in this
order: disabled, enabled, disabled, enabled, disabled, enabled. Each process
uses the same acrobat course, no brush commands, one 60-frame warmup, and four
consecutive four-second measurement arms:

| Arm | Dispatcher | FPS cap |
|---|---|---:|
| A1 | Original production `super(delta)` | 60 |
| B1 | Mechanically source-matched timed dispatcher | 60 |
| B2 | Mechanically source-matched timed dispatcher | 60 |
| A2 | Original production `super(delta)` | 60 |

The measurement portion is 16 seconds per process. Keep the original gameplay,
physics rate, time scale, v-sync policy, renderer selection, Rapier settings,
scene and native worker policy. The existing diagnostic command requests
`opengl3_angle`; record the actual renderer and device readback from each
process. Native worker request zero means automatic selection, not zero workers.
Both profiling states retain the same existing bounded native participation
sampler. Report configured capacity and observed completed-phase claimants
separately from CPU utilization.

Use `godot/tests/performance/test_main_rapier_thread_cpu_windows.gd` through
`tools/performance/rapier_thread_time.py`, preserving its source-restoration
checks, live bridge state check, wall clocks and enabled-state counter
calibration. No production optimization, dependency change, scheduler retuning,
thread-count override or alternate gameplay workload belongs to this campaign.

## Capture, lifecycle and failure retention

**Planned:** attempt WPR using the ordinary available capability. Its initial
status is not recording. Do not alter profiling privileges, security policy or
an unrelated recording to obtain a trace. Record the actual status, attempted
command, exit code and capability failure if recording is unavailable. Stop a
recording only when this campaign successfully started it.

Retain the existing per-thread `GetThreadTimes`, cycle and QPC fallback alongside
the production monotonic `space_step()` timer. Preserve the enabled-state busy
and sleep calibration. Counter units do not establish effective accounting
resolution; keep the existing 15.625 ms sensitivity allowance explicit as an
assumption rather than a Windows API accuracy guarantee. The fallback alone
cannot distinguish blocking from scheduler descheduling or exclude computation
on other threads.

For every process retain command, timeout, exit, full output, all four frame and
callback distributions, native/Rapier progress, actual worker participation,
bounded-buffer status and joined shutdown. Preserve failures and incomplete
runs as such. Only campaign-owned processes and traces may be retired; unrelated
existing application sessions remain outside this experiment.

## Prospective classification and comparison

Apply the existing registered rules to aligned `space_step()` events over
40 ms. Require at least three completed trials in each profiling state and at
least twenty qualified long events. CPU dominated requires at least 80% of long
events to meet at least 80% CPU-running occupancy; off-CPU dominated requires
at least 80% to meet at least 60% not-running time. Preserve counter sensitivity,
timing-boundary exclusions, unknown coverage and attribution limits.

Compare enabled and disabled frame interval p50 and p95 on this same host using
the existing 20% perturbation gate, while also reporting callback and step
medians, tails, event counts and absolute changes. Passing that frame gate does
not mean zero profiler perturbation. Missing alignment, unresolved attribution,
insufficient events or excessive perturbation yields an inconclusive result.
If the tail does not reproduce, retain that negative result; do not manufacture
long events or change the workload to reach the event threshold.

The TITAN RTX host is a separate cohort from the hosted Windows Server 2022
Microsoft Basic Render Driver runs. OS, CPU, scheduling environment and hardware
renderer differ together. Cross-host differences cannot isolate a GPU effect,
prove a renderer cause or establish a performance improvement. Analyze repeated
profiling comparisons within this local cohort and retain both cohorts' original
distributions without pooling their event counts to satisfy classification.
