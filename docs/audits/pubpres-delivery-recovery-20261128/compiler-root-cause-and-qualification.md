# PUBPRES portable compiler root cause and qualification — 2026-11-28

This record separates observed failures from source-based explanations and records the narrow focused Windows success. It does not qualify the complete extracted evaluator, the ordinary application, or physical-owner acceptance. PR #767 remains Draft/HOLD; merge and promotion remain unauthorized.

## Observed failure boundaries

The original portable GCC population was admitted against the immutable evaluator manifest: all **13,764** original files were present, with no missing, extra, or changed files. The admitted original `bin/g++.exe` SHA-256 was `eccc5963340f7b57805b3750efc182c25c6d4eddb828c8cee2b0f974a0d943ac` (GNU 14.2.0). The exact compiler reproduction reports that every queried program resolved inside the bundle, yet `collect2.exe` emitted `fatal error: cannot find 'ld'` for Unicode-only and combined-adverse paths. Its short ASCII, spaces, and parentheses controls compiled, linked, and ran; other path cases with process-observer refusals remained failures. See [the authenticated reproduction summary](original-compiler-reproduction.json) and [run 46164685636, artifact 15271386911](https://github.com/techrote/cybersand/actions/runs/46164685636/artifacts/15271386911) (artifact SHA-256 `d4672baa044661adb1e12f80e7fcc6e8141c7ce43c4b5be7fccc2e9e40f8696c`).

The subsequent per-process UTF-8 metadata candidate crossed a different boundary. Under Unicode paths `collect2` now launched the bundled GNU BFD `ld.exe`, but BFD could not open existing startup objects and CRT/library files, including `crt2.o`, `crtbegin.o`, `libstdc++` and other CRT libraries. This was not evidence that the linker binary was absent. The six-path record preserves the exact failures and the lack of a World receipt at this stage: [run 46171025142, artifact 15272964357](https://github.com/techrote/cybersand/actions/runs/46171025142/artifacts/15272964357), also summarized in [utf8-linker-file-open-refusal.json](utf8-linker-file-open-refusal.json).

## What the source establishes—and what is inferred

The runtime observations establish two Unicode-path failures: first linker-program discovery by the original `collect2`, then file opening by GNU BFD 2.44 after the UTF-8 process metadata allowed `ld.exe` to start. The first failure is consistent with the Unicode-only control boundary and GCC 14.2 `collect2` program-search code, but the evidence does not include binary disassembly or a source-reproducible rebuild of the admitted executable.

For the second failure, the upstream GNU Binutils 2.44 source inspection found a UTF-8 byte-count/wide-buffer separator defect consistent with the observed BFD paths. That is a **source-supported diagnosis**, not proof that the binary was disassembled or rebuilt from that source. The local record preserves the upstream source archive SHA and explicitly limits the claim. Microsoft’s [UTF-8 code-page guidance](https://learn.microsoft.com/en-us/windows/apps/design/globalizing/use-utf8-code-page) and [application-manifest `activeCodePage` contract](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests#activecodepage) support the process-local metadata approach; they do not establish that GNU’s driver or linker handles every Unicode path.

## Bounded toolchain correction

The copied GNU 14.2 toolchain retains its compiler, front end, assembler, `collect2`, startup objects, GCC support libraries and CRT. The UTF-8 repair adds a per-process Fusion manifest declaring `activeCodePage=UTF-8` to the registered GNU executables. Its admission and readback bind original and prepared file hashes, resource bytes/metadata and PE section evidence. An initial strict verifier correctly refused `bin/as.exe`: Windows inserted `.rsrc` into this resource-free image and moved the final `.reloc` section. The captured `.reloc` bytes, size and flags were unchanged; its RVA and raw pointer moved as the new section was inserted, while other non-resource section bytes remained exact. The later bounded verifier models that specific relocation-table transition instead of ignoring arbitrary non-resource changes. The later hosted linker-file-open run confirms all 15 pinned GNU executable resource transformations and independent static proofs passed before the remaining BFD link failure. The failure and correction trail is preserved in [the insertion diagnostic](utf8-resource-insertion-diagnostic.json), [the bounded relocation correction record](utf8-relocation-correction-local.json), and [the UTF-8 candidate validation record](utf8-candidate-local-validation.json).

UTF-8 metadata alone did not repair BFD file opening. The selected linker repair therefore retains GNU 14.2 and selects only the source-pinned GNU-compatible LLVM-MinGW **LLD 23.1.0** through `g++ -fuse-ld=lld`. The pinned 2026-08-26 archive is 190,721,391 bytes with SHA-256 `ae601f4e0f72bbdf441ad2df8bb16f037e2e9251559ea6b37b4057aef39c06c3`, upstream LLVM commit `ea7d852a70e8bdfaf601d6626a760f9771b2c4b4`. The staged closure contains the linker and its three non-system DLLs in both GNU search locations, plus six license/notice files: **14 pinned binary/license rows**. A source-bound marker binds this closure to the verified GNU compiler receipt; malformed, foreign or changed LLD proof refuses selection. See [the LLD controls](lld-candidate-local-controls.json) and [the official release archive](https://github.com/mstorsjo/llvm-mingw/releases/download/20260826/llvm-mingw-20260826-ucrt-x86_64.zip).

## Focused Windows result

The source-bound focused campaign passed on commit `c04f4b8ae5e0f535837056b24f7123790d84cf76`, tree `67d05919c101a223a0f7d3f282cb7655f89c2180`. The executed source identity records `tools/ci/portable_compiler_utf8.py` at SHA-256 `ca0044690aaed75c52e252eb37fa869ebc16ad5fe50581fd89336600776723c7` and `tools/ci/portable_lld.py` at `5e52d38e8fe51b151e650496d326715893800abc3748c7dabcfbb7bca03eb1f5`. All six registered path controls passed real compile, link and executable checks: short ASCII, spaces, parentheses, Unicode, nested, and combined adverse. Each observed the bundled `g++`, `cc1plus`, `as`, `collect2`, and `ld.lld` roles without missing roles or observer errors. The actual Materials Lab route then created the candidate and completed reference and candidate World builds/runs with the verified linker. The scenario was `(first=2, second=3, seed=17, ticks=120, workers=1)`; Sand density changed from 1600 to 1601 and the compiled native comparison receipt was produced.

During that World route, the packaged Python and both generated World executables had per-executable outbound firewall rules. Each generated probe rule’s path, byte length and SHA-256 matched the corresponding reference/candidate executable receipt. Windows Firewall service and all three profiles were enabled at preflight and postflight. The receipt records the actual child linker as `ld.lld.exe` inside the bundle and no original BFD `ld.exe` process. Path/process sampler warnings and the single uncorrelated observation received no credit; all required correlated roles were still present. The three original Unicode negative-control retries remain behavior-only evidence: expected missing-`ld` error, no executable, no `collect2` path credit, and no full-chain credit.

The concise result and artifact identities are in [focused-windows-success.json](focused-windows-success.json): [run 46174511004](https://github.com/techrote/cybersand/actions/runs/46174511004) and [artifact 15275506430](https://github.com/techrote/cybersand/actions/runs/46174511004/artifacts/15275506430), artifact SHA-256 `d6d410c3be641274ff32a2e1b3ded5cabed5462c72771b53f82f2c3884dd1bfc`, witness SHA-256 `bd92db4cdba3684900a42d58af7700f16c27009e1bcc4b75a66ef328b2a9de83`. The longer local production-World control took 95.17 seconds at source `78a7c84ef540af600343e38ca6f7aa4cd1a68675`; its raw JSON is `C:\Users\_\AppData\Local\Temp\pubpres-lld-local-production-world.json` (532,266 bytes, SHA-256 `fa3bb0735359812475c8a686d50a277f6b21db0d4c9f60b679ef102a316ae3cb`). It is supporting local evidence only: that local C++ source tree lacked the unused `bin/make.exe` alias; the other 13,763 original files matched. It is not a complete compiler-population or extracted-package qualification.

## Native runtime custody and remaining acceptance

These compiler changes do not modify production C++ inputs. The existing native objects remain bound to the original native build; they were not rebuilt or relabelled as a newer compilation. The established custody record accounts for **115 native inputs plus 8 build inputs (123 total)** and requires exact input equivalence before reuse. The source/runtime and original build identities are in the [independent delivery custody record](../pubpres-mainline-convergence-20261128/independent-delivery-custody.md); the original native build source remains `b7c79f072d8d389fb3cc0e3ae0e933e9bc5a9d34`.

**Complete extracted-package qualification is pending.** The focused six-path and offline World result does not establish a newly built 1.4 GB evaluator, independent archive extraction, shipped launcher, durable save/reopen, downstream extracted features, runtime module loading, diagnostics collection, or final payload integrity. Do not promote this evidence to a complete evaluator pass. Physical owner acceptance remains HOLD and PR #767 remains Draft/HOLD.
