## Implemented ownership and scheduling contract

The opt-in scene constructs one real native World and its ObjectShard registry
inside one exclusive native worker thread. Main owns every Rapier RID and all
geometry/pose presentation. A copied value publication crosses the thread
boundary; native pointers, physics objects and mutable aliases do not.

Session identity, lifecycle generation, operation sequence, body incarnation,
geometry revision and pose serial fence different kinds of authority. The host
allows one in-flight protocol operation. A structural promotion reserves a
disabled real Rapier body, commits the native World debit, installs terrain and
occupancy, and activates only after the required installation evidence. Late or
duplicate receipts cannot re-create a retired body or session. Every real motion
segment waits for its exact native applied acknowledgement before another
segment may run. Physics never advances independently on the worker.

Cancellation before commit leaves World ownership intact and completes the
already-started physical interval for existing bodies. Cancellation after debit
retains/quarantines inactive shard inventory and requires explicit disposal
recovery; it does not invent a rollback. Terrain acknowledgement applies the
native occupancy mask before `ReadyToActivate`.

Ordinary edits and owner-aware cuts use the same authoritative native material
path. A moving cut captures the displayed owner, incarnation, cell, geometry,
pose and material witness. It never re-hits a newer pose to make an old action
succeed. A changed witness produces the visible `TargetChanged` refusal. The
scene dispatches pointer intents before polling and opens an input window after
each completed displayed tick; this permits fresh cuts into an awake falling
body while continuous progression remains enabled.

The host queues at most 32 actions in addition to its single in-flight operation;
at most four actions run before a requested semantic tick. Worker data and
control channels have separate capacities of 32 and eight. Command parameter
value payloads are bounded to 64 KiB, with bounded nesting and node counts; this
is not a whole-envelope or allocator memory limit. The scene retains at most 256
pending pointer intents. Rejection or backpressure has a reason. Reset/stop
records terminal dispositions for host-admitted queued and uncertain in-flight
actions; the UI also records cancellation counts for unadmitted pointer intents.
A prepared promotion or pending geometry
acknowledgement does not silently steal material or authorize further physics.

Each completed physics interval publishes a logically consistent native
material/geometry/pose state. Main uploads that state after its last receipt
poll. The rendered timing receipt is single-use and belongs to that exact
publication after `frame_post_draw`. A headless run cannot claim visible-frame
latency. Retained rendered reports expose counts and latency distributions,
not a raw per-presentation timestamp/sequence ledger or monitor scanout.
Deliberately delayed receipts keep the previous coherent frame; a
15-second expiry enters visible Held/ShutdownHeld custody instead of resuming
an operation with uncertain outcome.

## Continuous play and useful development controls

The feature launcher has one explicit M3 entry and `--objectshard-m3`. The owner
screen preserves all eleven 001R presets and offers Erase, Wood, Sand, Water,
Fire, Ignite and Inspect while simulation continues. Pause, single-step and
resume retain the current owner and complete any admitted interval. Reset and
scenario replacement dispose and join the old owner before creating another.
Default scenes use 192×128; larger named cases use 256×160 and 320×192.

F2 requests an asynchronous owner shutdown. The current scene stays alive until
native disposal, stopped-thread join and main-thread RID release complete.
Repeated F2 is idempotent; window close upgrades the destination to process exit,
and that choice survives an explicit retry from ShutdownHeld. Pending reset or
scenario replacement cannot create another owner after navigation begins.
Closing controls refuse new material input visibly. Completion is fenced to the
current scene both before and during the deferred handoff, and the launcher's
previous window-close policy is restored only after disposal. This is controlled
navigation, not a universal cleanup promise for arbitrary external forced scene
replacement.

The tested loop is a genuine support cut, native ownership transfer, real Rapier
fall/contact/settling, followed by further World and moving-owner edits. The
three-body sustained test also exercises real Fire/Smoke chemistry, authored

retained ledger does not show Sand ingestion or Water extinction; those

author actual native materials;
