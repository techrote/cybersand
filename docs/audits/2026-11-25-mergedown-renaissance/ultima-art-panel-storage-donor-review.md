## Defects and repair boundaries

The original Linux controls preserve two real false acknowledgements. A limited write left a 128-byte unreadable settings file after a successful acknowledgement, replacing the previously readable configuration. The corresponding pending-history control acknowledged a truncated 128-byte receipt, replacing the earlier valid receipt. These are preserved failures, not hypothetical reasons to expand the integration.

The settings repair retains the existing profile-admission guard and maximum encoded size. It writes and verifies a closed staging file through the shared `workbench_file_transaction.gd` utility, then uses the already accepted native atomic replacement primitive. A failed commit reports an owned input error; a successful retry clears only that error. The utility is therefore a dependency of this new panel donor. The earlier `a03b83eab8cba84f095043888075b370659d1aac` streaming export/event repair uses its own bounded archive verifier and does not depend on this utility.

The pending-history repair preserves the schema, item identity, epoch, frozen projection, ordering, count, and size checks. It uses short random staging names suitable for Windows paths, checks the write result and flush error, closes and verifies the complete payload, and performs the existing native replacement. Only verified publication advances the receipt clock and records the item's order and file identity. A failed publication preserves the earlier receipt and leaves the new item unacknowledged. This does not introduce automatic journal or previous-conversation restoration; Art conversations remain session-only.

Neither repair promises a multi-file transaction, cross-process locking, power-loss recovery, or an `fsync` guarantee beyond the existing implementation. Native source and runtime bytes are unchanged by these donors.
