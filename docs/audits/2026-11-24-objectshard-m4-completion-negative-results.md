# ObjectShard M4 completion retained negative results

The completion campaign retains failed observations and identifies which
boundary each one exercised. A corrected fixture does not erase its earlier
failure, and a source correction does not establish execution on a new runtime.
Final qualification must name its exact source, runtime inputs and workload.

All three ran headless and submitted zero rendered frames. Their callback
rates are not displayed FPS. The first tower measurement started before the
native inventory activation barrier and omitted body dimensions; later
profiles wait for installed ownership and exact geometry before sampling.
The reported occupancy time includes relocation, and the Main receipt-pump
time includes waits and nested stages. Adding these values would double-count
cost.

The measured optimization targets unnecessary no-observer GCR sweeps,
unchanged compositions with still-current native receipts, and full-canvas
traversal where only a sparse occupied raster is needed. It preserves sorted
relocation order and requires refusal/retry parity tests. Its benefit must be
established with fresh source-bound before/after runs.

## Acceptance boundary

The owner's earlier below-10-FPS observation remains a physical Windows/NVIDIA
acceptance question. A cloud software-renderer run can establish actual
renderer submissions and coherent pixels, but cannot establish physical
monitor presentation, driver behaviour or owner playfeel. Runtime custody,
native progression, render submission and physical owner acceptance must stay
separate in the final decision.

No result in this record authorizes a merge, Ready promotion, production
runtime publication or default activation.
