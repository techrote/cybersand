## Memory accounting and compact fence review

The negative f11 matrix reached **6,670,496 requested C++ bytes**, above the unchanged 6,291,456-byte ceiling. Seven workloads each failed live and peak limits. The memory repair changes only a private ingress-history key from a 24-byte full Handle to an eight-byte monotonic shard ID. The complete record falls from 32 to 16 bytes; two reserved arrays of 12,288 records therefore save exactly **393,216 bytes**. Their capacities are unchanged.

The compact key is not an authority token. Public material/pose/ingress paths still validate complete session, ID and generation. `Registry::reset` retires existing entries but does not reset `next_id_`; `prepare` refuses identity exhaustion. Fence refresh resolves the ID through the bounded current body roster, then uses the body's full Handle in `Registry::find`. `pocket_fenced` first validates its full supplied Handle. The reset, retired-session and wrong-generation checks protect that separation. This inspection found no recycled-slot or RID path able to revive an old fence as a different material owner.

Final observed peak is **6,277,280 bytes**, only **14,176 bytes below** the default-canvas ceiling. This narrow margin must remain visible. It is not a universal upper bound for larger scenarios, arbitrary maximum-area payloads or future features. The three-body peak is 1,608,008 bytes above the fresh historical control; complete discovery and contact-history storage have a real cost.

The allocation probe intercepts ordinary and over-aligned C++ `new`/`delete`, tracks requested bytes and excludes pre-reserved measurement arrays from the coordinator interval. Construction and steady-state windows are distinct. Zero recurring C++ allocations is supported in the measured workloads. This does **not** measure process RSS, allocator metadata, direct C allocations, thread stacks, Godot, Rapier or GPU memory. Snapshot native counters are an accounted lower bound and cannot replace that global allocation measurement.

The constructor bounds the resident canvas, registry count/area, exposure capacity, transfer budget, shape capacity and coordinate envelope. Discovery and geometry buffers remain finite. This supports bounded resources, without claiming that every maximum-capacity configuration meets the default-canvas timing ceiling.

## Timing interpretation and focused falsification

The retained paired experiment contains all three registered alternating pairs. Its representative three-body p50 increased **3.28%**, and wake-burst p50 increased **4.43%**. One-body p95 increased **35.24%**; wake-burst p95 increased **12.82%**. These tails are visible, and all corresponding ceilings passed. The comparison supports no general frame-rate improvement claim. The separate admission-refusal speedup measures repeated unchanged component queries and must not be substituted for overall frame timing.

The reviewer challenged a selective difference in the final matrix: dormant/wake p50 was 601.697/634.585 µs, versus 340.266/349.521 µs in the paired repaired iteration. A bounded, preregistered eight-process probe compared those same frozen pre-timer and final executables, two observations per source/workload, with every result retained:

| Workload | Pre-timer p50 observations, µs | Final p50 observations, µs |
| --- | ---: | ---: |
| Dormant twelve | 604.255; 596.196 | 620.912; 592.876 |
| Wake twelve | 648.553; 627.423 | 630.729; 658.646 |

Both binaries reproduced the slower cohort. The earlier-to-later increase is therefore **not demonstrated as a final timer-delta regression**. The probe does not establish a unique cause, CPU exclusivity, statistical equivalence or a new full qualification result. The original slower final measurements remain unchanged. The raw probe and its declared sequence are retained under `targeted-timing/`.

The final contact timer correctly includes historical-only ingress/fence work that f11 omitted. Overall frame wall time already included that work. Occupancy, contact and relocation scopes overlap; their percentiles cannot be added as disjoint costs. Native geometry age zero follows immediate synthetic acknowledgements. It does not establish actual main-thread installation latency, and the benchmark explicitly has no Rapier stepping or rendered presentation. Three construction/promotion samples are descriptive, not qualified p99 bounds.

## Supplemental actual Windows evidence and package repair

The reviewer independently checked the downloaded **f11** Windows evidence against its exact commit: 26 Lab inputs, 116 native inputs and 18 qualification-tool inputs all matched Git, with zero mismatches. Another **454 independent checks** verified complete retained profile samples, declared percentiles, workload inventories and all limits. The headless 56-limit and rendered 80-limit profile matrices passed. Each of eight workloads retained 1,200 samples.

Representative f11 Windows owner-thread p95 was **3.932 ms** for three reacting bodies headless and **7.130 ms** rendered. The largest rendered owner-thread frame was **13.582 ms**; the largest retained presentation interval was **32.023 ms**. These are hosted Windows observations of f11, not final native-514d execution, a GPU benchmark or physical Windows 11/NVIDIA acceptance.

The old delivered-ZIP qualification failed because the shipped Windows PowerShell path could not resolve `Get-FileHash`. That is a real delivery failure and remains distinct from the passing unpackaged Lab. The f480 package-only repair uses streaming `[Security.Cryptography.SHA256]` over exact file bytes, retains the native/Rapier/source identity checks, and disposes streams and hash objects. It does not suppress verification failures or alter manifest values after packaging.

The new actual-Windows negative probe shadows `Get-FileHash`, then deliberately alters a verified extraction's `READ-ME.md`. Passing requires the specific changed-file hash failure; an unrelated nonzero exit cannot satisfy the gate. The extraction is restored byte-for-byte in `finally` and fully reverified. The delivered ZIP itself remains immutable. The reviewer independently ran all **36 Python tooling tests**, including expected refusal, timeout restoration and unrelated-failure rejection. These tests are not Windows command execution.

The workflow's new explicit `[objectshard-windows]` marker only selects the existing Windows build, actual Lab and delivered-ZIP jobs on existing ObjectShard experiment branch families. Linux remains visibly skipped for that request; ordinary markers and required-check contexts are unchanged. It is safe only to describe the skipped Linux lane as unexecuted and reuse its existing evidence through exact native-input equivalence. This review verified that equivalence for f480 against 514d.

**Final package verdict remains pending the repaired archive's actual four-path verification, boot and full extracted-package replay.** Until those receipts and the delivered ZIP SHA-256 exist, this review approves the source correction, not a complete Windows delivery. All PRs remain Draft/HOLD and owner physical acceptance remains unrecorded.
