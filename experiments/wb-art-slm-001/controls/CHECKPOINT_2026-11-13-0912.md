## Implemented: chronological native receipt admission

Review of the unchanged pinned `evaluation/native_replay.gd` shows that `replay_case` submits the Art plan, obtains native draw receipts, captures the completed 512×512 draw World, then captures Undo, Redo and save/reopen Worlds, in that order. Existing Controls auditor validated the four capture **hashes**, but grouped draw receipts and captures into separate arrays without checking their original interleaving in `native-receipts.jsonl`. Reordered or post-capture draw events could therefore have the same final stored-material and summary hashes while violating the supposed draw→history chronology.

`controls/audit_v11_native_pairs.py` now refuses a history capture before the first completed draw receipt and refuses any further draw receipt after the first history capture. This is strictly an additional fail-closed native-evidence check; it preserves source IDs, all 15 global native gates, the previously fixed crop-tamper diagnostic, the exact draw/Undo/Redo/reopen hash checks, and the existing receipt reconstruction. It changes neither the frozen v1/v1.1 compiler nor native execution behavior.

Two new adversarial tests in `controls/test_audit_v11_native_pairs.py` reorder an existing case's chronological events (before first draw, and extra draw after first capture) and recompute the published raw-receipt hash, ensuring the new checks cannot be bypassed by updating metadata. The test suite now contains **15 methods**. Implementation commit `baf95f41562dc300794f2386cba670d97e5ad8a7`; adversarial test commit `9a4b1e476d43d52af7b441b094f61cec6e6056c2`.
